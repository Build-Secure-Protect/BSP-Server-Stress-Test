# Changelog

All notable changes to this project are documented in this file. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- With BSP-Core 1.4.5 or newer, a bot's Shatter Totems are forgotten when it leaves (BSP-Core's `BspTotems.forgetPlayer`: carried and placed totems taken, every record of them dropped, nothing given back), and `/stress cleanup` has BSP-Core forget the totems of every bot name up to `limits.maxBots`, also those a server that stopped mid-run left. The test server no longer needs `grantTotemOnFirstJoin = false` for bots to leave nothing behind. With an older BSP-Core the log says once that totems are not forgotten. Built against BSP-Core 1.4.5 (still optional).

### Added
- `/stress set <option> <amount>`: changes one option of the running test at once, for example `/stress set setups.create.millstones 20`. An option the test does not have is added, `0` takes one out, and only the hard limits in `settings.toml` cap the amount. The step going ends (measured as any) and a step marked "by hand" begins, so the report shows each change at the step it happened; from there the option steps on with the rest, and one set above its ceiling holds there. For this test only: chat shows the `/stress profile` commands that would keep it for the next one. Refused when no test is running.

### Changed
- Standing and wandering bots spread far apart, as real players do: each bot has its own spot, `bots.spacing` (now 1,000 blocks by default, up to 100,000) apart on a square spiral out from each place, and only spots whose land the bot would see (the server's view distance around it) is already generated are used, so they never make new land. Whether land is generated is read from the chunks' saved status, without loading anything. With fewer generated spots than bots, bots share them and the log says how many there are. A wandering bot wanders the square around its own spot, only to points on generated land. Flying bots are unchanged (making new land is what they are for).

### Fixed
- The report no longer says the server kept up with 20 ticks a second when it did not. It judged by the average tick alone, so a server doing 11.7 ticks a second with 16 ms ticks was reported as keeping up. Now a server is behind below 19 measured ticks a second as well as above a 50 ms average tick, and when its ticks are short but too few, the report says how much of each second went to work done between ticks (chunks loading and being generated, with the count of new ones, Java pausing to clear memory, catching up), in measurements and in runs.
- Bots no longer leave a moment after joining with "Internal Exception: java.util.NoSuchElementException: splitter". A bot's connection is now laid out as a real one's (`timeout`, `legacy_query`, `splitter`, `decoder`, `prepender`, `encoder`, `packet_handler`), so plugins and mods that hook their own handlers in by those names on every join find them, and it carries what a Forge client with every mod and channel of the server hands over in its login handshake, so Forge and the mods see an ordinary modded player. Any other error in a bot's connection is logged once per kind with its stack trace and ignored for the bot, instead of disconnecting it.
- Bots no longer leave a moment after joining on a server where some packet cannot be encoded for them (a mod's packet that expects a real client's connection): such a packet is dropped for the bot, with one warning per kind of packet in the log naming it, instead of closing the bot's connection. Bots' connections also give a loopback network address, as code written for real connections expects. When a bot is disconnected all the same, the log says what the server or the mod gave as the reason.

### Added
- Working setups for more of the pack, each offered only when its mods are loaded:
  - `setups.create.train_line`: a 14-block straight track with a station near each end and one small train (a small bogey, three slime blocks, a seat between two controls blocks facing both ways) shuttling between them on a schedule, waiting 3 seconds at each. Assembled by Create's own station assembly, with a schedule item in the station; its conductor is a pig with its AI off. `/stress cleanup` also takes out of Create's records any train a train line left.
  - `setups.mekanism.machine_line`: a creative energy cube powering an enrichment chamber (iron ore), a crusher (cobblestone) and an energized smelter (raw beef) through universal cable. The cube is charged when placed (placed as a block it starts empty).
  - `setups.refinedstorage.item_network`: a creative controller and cable; an importer pulls cobblestone from a chest the mod fills and an external storage pushes it into a chest the mod empties.
  - `setups.ae2.item_network`: an AE2 controller on a creative energy cell, an ME interface the mod feeds and an ME chest with a 4k cell storing what the network takes in; the cell is swapped for an empty one when full.
  - `setups.thermal.machines`: a pulverizer, a redstone furnace and a sawmill around Powah's creative energy cell.
  - `setups.enderio.machines`: two SAG mills and an alloy smelter, each with a basic capacitor fitted, around EnderIO's creative power block.
  - `setups.industrialforegoing.machines`: three resourceful furnaces whose energy the stress mod tops up every tick (no creative power block exists outside development).
  - `setups.botania.exoflame_furnaces`: an Exoflame bound to a creative mana pool, heating three furnaces of raw beef.
- Feeding reaches a machine through every side it offers (some take items only on certain sides), keeps fitted parts such as capacitors, throws away fluids a machine makes, and empties the machine's item stores before it is removed so nothing drops.
- `tools/prepare_libs.py` copies every family's mods and the mods they need (GuideME, CoFH Core, Architectury, Cloth Config, Titanium, Curios, Patchouli) into `libs/`.
- Create's moving contraptions as working setups. `setups.create.bearing_rotor`: a creative motor turning a mechanical bearing with a plate of slime blocks on it (`setups.rotorSide`, 5: 25 blocks), which the bearing builds into one moving piece and spins forever. `setups.create.piston_line`: a creative motor driving a sticky mechanical piston through a gearshift, with four extension poles; every 4 seconds a redstone block beside the gearshift comes or goes, so the piston builds its face of slime blocks (`setups.pistonSide`, 3: 9 blocks) into a moving piece, pushes it 4 blocks, puts it down, and pulls it back the same way. The whole path the face and poles travel is kept clear and recorded. Slime holds the blocks together without Create's super glue. Every moving piece carries the mod's tag from the moment it appears, so one left by a server that stopped mid-run is refused when its chunk loads; on a normal stop the bearing or piston forgets its moving piece and the piece is discarded before the setup is removed, so no blocks are put down anywhere.
- Working setups (`setups.<mod>.<name>`): a mod's machines powered from the mod's own creative source and fed, so they really work. The level is how many stand (5 more each step, up to 100), in their own grid `setups.aboveWorld` (40) blocks above the world options' contraptions, `setups.gridSide` (8) to a side, corners `setups.spacing` (16) apart, listed in `placed.json` so a stop, a step down and `/stress cleanup` remove them. Every 2 seconds each setup's input gets 16 of a cheap item its machine can process and whatever else it holds is thrown away, so it never backs up. Anything a removed setup holds is emptied first, so nothing drops. They are offered only when their mod is loaded, appear in `/stress options` and `options.txt` as "working setup", and the new starter profile `setups_only` includes them all.
- Create's setups, each turned by a creative motor at 64 RPM: `setups.create.press_line` (three mechanical presses in a row over depots of iron ingots, pressed into sheets), `setups.create.millstones` (three millstones, each on a shaft above its own motor, grinding cobblestone), `setups.create.fan_smoking` (an encased fan blowing through a lit campfire over three depots of raw beef: bulk smoking), `setups.create.belt_line` (an 8-block belt carrying cobblestone from one end to the other between two stone blocks). Create is never a dependency: the mod finds its blocks by id and calls it only to set a motor's speed and lay a belt.
- `tools/prepare_libs.py`: copies a mod family's jar from the server's `mods/` folder into `libs/` (never committed) so dev runs and GameTests load it.
- World options, built from plain vanilla blocks in their own grid `world.aboveMachines` (40) blocks above the machine grid at each chunk place (or spawn), `world.gridSide` (16) to a side, corners `world.spacing` (8) blocks apart, layers 16 blocks apart. Only placed where every block of one is air, so no build is overwritten; listed in `placed.json` with the machines, so a stop, a step down and `/stress cleanup` (also after a server stopped mid-run) remove them. The level is how many stand: `world.redstone_clocks` (two observers facing each other on a stone base with a redstone lamp and a line of dust, pulsing every 2 game ticks; 25 more each step, up to 500), `world.hoppers` (four hoppers in a square passing a stack of cobblestone each round and round; emptied before they are removed, so nothing drops; 25, up to 500), `world.fluids` (a 7 x 7 glass basin whose middle source is taken away and put back every 3 seconds, every fourth basin lava; 10, up to 200), `world.lighting` (glowstone swapped with stone every half second; 25, up to 500), `world.falling_blocks` (sand dropped 10 blocks onto a stone floor every 2 seconds; 25, up to 500). Contraptions that repeat their work are spread over the ticks so they do not all go at once.
- `world.random_ticks`: the level is the `randomTickSpeed` game rule (3 more each step, up to 30, capped by `limits.maxRandomTickSpeed`), put back when the run ends. The world's own value is kept in `config/bsp_server_stress_test/random_ticks.json` while a run has changed it: a server that stopped mid-run puts it back at its next start, and `/stress cleanup` does too. The game keeps game rules in the world's `level.dat`, the one thing a run changes there.
- `world.save`: the level is whole-world saves a minute (1 more each step, up to 12, capped by `limits.maxSavesPerMinute`); before each save every chunk the mod holds is marked as changed, so the save writes them all. A world with saving turned off (`/save-off`) is left so.
- The report's "time the timers do not see" also names random ticks and flowing water and lava.
- Explosions, set off every `explosions.everySeconds` (5) while a run includes them, in a blast area `explosions.distance` (300) blocks east of each chunk place (or spawn), at the next spot of a square spiral of 25 spots `explosions.spacing` (64) apart; the blast area's chunks are held ticking. `explosions.vanilla`: an explosion whose power is the level (TNT is 4; 8 more each step up to 128, capped by `limits.maxExplosionPower`), every other one keeping the blocks (only the work of finding what would break) and the others breaking them. `explosions.tnt_chain`: that many lit TNT in a tight cluster (20 more each step, up to 400). `explosions.<mod>.<block>` for each explosive in the catalogue: that many placed with a redstone block on top, which sets off any that answer to redstone (1 more each step, up to 10); the redstone block is taken away two ticks later, and an explosive that has not gone off after ten seconds is taken away and counted as a dud (the server log says how many when the run ends). `/stress cleanup` stops them too.
- Crowds: every mob in the catalogue is now an option of its own (`entities.<mod>.<mob>`, 10 more each step, up to 200), plus `entities.items` (dropped items) and `entities.xp` (experience orbs), 100 more each step up to 2,000. They are spawned on the ground around the chunk places (or spawn), one per block on a square spiral, so they crowd as farms do, over chunks held ticking. Mobs are kept from despawning; items never despawn and cannot be picked up; orbs are worth 1 each. A step up replaces any killed or merged since. At most `limits.maxEntities` (2,000) per option and `limits.maxSpawnedTotal` (10,000) in all. Every one carries the tag `bsp_server_stress_test`: one left in the world by a server that stopped mid-run is refused the moment its chunk loads, and `/stress cleanup` removes every loaded one.
- Bots take no harm (mobs still chase them): a dead bot would wait for a respawn that never comes.
- Idle machines: every ticking block in the catalogue is now an option of its own (`machines.<mod>.<block>`, 5 more each step, up to 100), placed in a grid in the air above the chunk places (or spawn): `machines.gridSide` (64) to a side, `machines.spacing` (2) blocks apart so nothing joins up, the first layer `machines.heightAboveGround` (20) up, then layer on layer. A block is only placed where the cell is air, so no build is ever overwritten, and without neighbour updates. The chunks under the machines are held ticking. All options together place at most `limits.maxPlacedTotal` (20,000) blocks. Every placed block is listed in `config/bsp_server_stress_test/placed.json` as it is placed; a step down, a stop or the end of a run removes them (only where the block there is still the one placed).
- `/stress cleanup`: removes every block a run placed (including what a server that stopped mid-run left, from `placed.json`), logs every bot out and lets every held chunk go. `/stress` and the server log say when an earlier run left blocks in the world.
- Moving bots, in three groups that share `limits.maxBots`: `bots.stand` (standing, spread out from the chunk places on a square spiral `bots.spacing` (48) blocks apart, on the ground), `bots.wander` (walking at `bots.walkBlocksPerSecond` (4.3) from one random spot to the next inside a `bots.wanderSquare` (200) block square around their place, on the ground) and `bots.fly_out` (flying from their place in a straight line at `bots.flyY` (160) and `bots.flyBlocksPerSecond` (20), each on its own heading, turning back at the world border, so they keep loading and generating new land). Bots are shared between the chunk places, or spawn. Moves load and send chunks as a player's movement does. `/stress bots <number> [stand | wander | fly]`; `/stress bots` shows each group.
- Bots: `/stress bots <number>` (and `/stress bots release`, `/stress bots` for how many) logs in bots named `SSTBot_0001` and on, with the offline-mode UUID of the name, as real players through the server's normal login: they are in the player list, every mod's login and logout run for them, chunks load around them, and the packets a player is sent are built and encoded, then thrown away. They are ticked by the mod, so they are never kicked for not answering. A bot kicked by the server or a mod is logged out properly. When a bot leaves, its player, stats and advancement files and its line in `usercache.json` are deleted. Bots never count as real players for `safety.allowRunsWithPlayers`. At most `limits.maxBots` (200).
- Bot options for runs: `bots.stand` and `bots.wander` (10 more each step) and `bots.fly_out` (5 more each step), up to 200.
- Held chunks, with the mod's own chunk ticket (`bsp_server_stress_test:hold`, named in analyses and in spark): `/stress chunks <number>` holds that many chunks at the saved places (or at spawn when none are saved), shared evenly between the places, each a square growing outward from its middle. The chat shows how many are held, how, where, and how many the whole server has loaded, with clickable keys [-100] [-10] [+10] [+100] [let go]. While any are held, the people allowed to use `/stress` see a bar at the top of the screen: "Chunks held 1,200 / 4,096 · loaded on the server 3,870", updated every second. `/stress chunks add <change>`, `/stress chunks release`.
- `/stress chunks mode ticking | loaded` (`chunks.ticking` in `settings.toml`, true): held chunks either tick (machines, crops and mobs in them work, as if a player stood there) or are only loaded.
- `/stress chunks place add <name>` saves the spot where you stand (`spawn` always means the world spawn), `place remove <name>`, `place list`; kept in `config/bsp_server_stress_test/places.json`. Changing places shares the held chunks between the new places at once.
- Two options for runs: `chunks.hold` (held chunks at the places; 256 more each step, up to 4,096) and `chunks.generate_fresh` (held chunks in land nobody has visited, 30,000 to 200,000 blocks from spawn inside the world border, a new spot each run, so every step generates new land; 64 more each step, up to 1,024). Everything the mod holds together never passes `limits.maxChunks` (4,096 at most). Nothing is saved: a restart lets every chunk go.
- The analyser, `/stress analyse [seconds]` (5 to 600, 30 by default): measures the server as it is, adding nothing, then looks at the world and writes the plain-English report beside its CSVs (`analyse.txt`). Besides the usual sections it says where the biggest crowds of entities are and what most of them are, where the biggest piles of dropped items are, what keeps chunks loaded besides players (the spawn area, `/forceload`, portals, and chunk loaders by the mod that placed them, each with where the first few are), and each dimension's tick time and counts. Its headline is said in chat. It only reads, so it can be used on any server.
- The watch, `/stress watch on | off` (off by default; `/stress watch` says how it is set): when the average tick stays above `watch.limitMs` (50) for `watch.overSeconds` (60), it analyses the server for `watch.analyseSeconds` (30) by itself, tells the people allowed to use `/stress` who are online and the server log, and then waits `watch.quietMinutes` (30) before it may again. Never while a run or another analysis is going. It reads the tick times the server keeps anyway.
- The plain-English report: every run and every `/stress measure` writes a text file beside its CSVs (`... .txt`). WHAT HURT MOST opens it in a few numbered sentences: the step with the biggest rise in tick time and what it added; the thing that cost most, its share of the tick, and why it costs ("Hoppers check every tick for items to pull in from above and to push out..."); the busiest place with coordinates; whether the server kept up with 20 ticks a second and where it fell behind; how much of the tick went to work the timers do not see; how many new chunks were generated and through which world generation mods; and memory when it is nearly full. Then STEP BY STEP, WORST PLACES, WORST THINGS (each with its reason), BY MOD, and ABOUT THESE FIGURES. Every number comes from a measurement. When a run ends the chat shows the same sentences and where the report is.
- The reasons ("why it costs") are a list in the language file: one for ticking blocks, mobs and other entities, and their own for hoppers, spawners, beacons, furnaces, sculk sensors, dropped items, experience orbs, villagers, lit TNT, falling blocks and Create contraptions and trains.
- Run steps are named "step 2 (test load: 10 ms wasted every tick)" and the baseline "step 0 (the baseline, nothing added)".
- Timers on every block entity's and every entity's tick while something is being measured (a run's step, `/stress measure`): the time is added up by what ticked (the block, or the kind of entity), by chunk and by mod. The chat summary of a measurement now ends with the five busiest things ("Busiest: Hopper 1.20 ms a tick (340 of them); ..."), the three busiest chunks with their coordinates and what cost most in each, and what the timers themselves cost; each step of a run names its busiest things. A second CSV beside each figures file (`... timings.csv`) lists the 50 busiest blocks and entity types, the 50 busiest chunks and every mod, in milliseconds per tick and as a share of the average tick. When nothing is being measured the timers only read one flag. If a timer cannot hook in on a server, the summary says so instead of showing figures without it.
- The options catalogue: when the server starts, the mod lists everything it can be tested with, from the mods it loaded: every block whose block entity ticks on the server ("ticking blocks", `machines.<mod>.<block>`), every mob that can be summoned (`entities.<mod>.<mob>`), every explosive (`explosions.<mod>.<block>`: TNT and its kin, and blocks whose id or class name ends in tnt, bomb, nuke, explosive or dynamite), and 17 general options every server has (all ready since the world options). Names are in English, read from each mod's own language file. Each entry is ready, coming with a later task, or left out with the reason (no item, so a technical block; or listed in `catalogue.leaveOut`). Wall forms of blocks are listed under the block their item places.
- `config/bsp_server_stress_test/options.txt`: the whole catalogue by mod, with the id to put in a profile.
- `/stress options`: rebuilds the catalogue and says how many ticking blocks, mobs, explosives and general options the server has, how many are ready, coming or left out, and which mods give the most. `/stress options <mod>`: that mod's options with their ids (40 in chat, the rest in the file).
- `catalogue.leaveOut` in `settings.toml`: blocks and mobs never offered, by id or `mod:*`. By default command and structure blocks, BSP-Core's Shatter Totem, Decoy Totem and ghost block, the Ender Dragon and the Wither.
- `/stress profile show` says how many catalogue entries the profile covers on this server and how many are ready.
- Stress runs: `/stress start <profile>` runs one profile at a time. Step 0 adds nothing and measures the server as it was; each later step raises every included option by its step, up to its ceiling. A step lasts the profile's `stepSeconds` (60) and is measured after its `settleSeconds` (10); each step's figures are said in chat. A run ends when every option has reached its ceiling, when the average tick over the last `safety.stopWindowSeconds` (20) passes the profile's `stopAverageMs` (50), at once when one tick takes longer than `safety.emergencyTickSeconds` (10), on `/stress stop`, or when the server stops. Ending releases everything the run made and writes every step's figures to a CSV in `reports/`.
- `/stress ramp up | down | hold | auto`: step up or down by hand now, hold the run on its step, or let it step on its own again. `/stress status`: the profile, the step, where each option is, and the last measured step.
- Real players are kept out of the way: a run will not start while someone online is neither a bot nor allowed to use `/stress`. With `safety.allowRunsWithPlayers = true` it starts only when the same `/stress start` is given twice within 3 seconds.
- Profiles in `config/bsp_server_stress_test/profiles/<name>.json`: which options to include and leave out (`*`, a category such as `bots.*`, or one option; leaving out wins), each option's step and ceiling, the timing and the limit. `/stress profile list | show | new <name> [from] | include | exclude | forget <name> <pattern> | step | ceiling <name> <option> <amount> | timing <name> <stepSeconds> <settleSeconds> | limit <name> <ms>`. Starter profiles `everything`, `pre_generated` (no new land), `players_only`, `machines_only` and `test_load` are written when missing and never over an edited file.
- Hard ceilings in `settings.toml` (`[limits]`): `maxBots` 200, `maxChunks` 4096 (64 x 64, the most allowed), `maxExplosionPower` 128, `maxMachines` 2000, `maxTestMilliseconds` 200; no profile goes past them.
- The test load, option `test.spin`: wastes 5 ms more of every tick each step (up to 60), a cost known exactly for trying runs and their stop rules (profile `test_load`).
- `/stress measure [seconds]` (5 to 600, default 30): measures the server as it is and then says in chat how many ticks it managed per second, the average and worst tick and the share over 50 ms, the five busiest dimensions (average and worst tick, chunks loaded, entities, ticking block entities), and the whole server's chunks, entities, ticking block entities, players, new chunks generated and memory. The same figures, every dimension included, go to a CSV file in `config/bsp_server_stress_test/reports/`. One measurement at a time.
- The measuring core every later test uses: each tick's time from the server's own tick history, overall and per dimension; new chunks counted as they generate; the counts read at the end.
- `/stress` for operators at level 4 and BSP-Core admins: the version, the folder the mod writes in, whether runs may start while real players are online, and whether BSP-Core is installed.
- Settings in `config/bsp_server_stress_test/settings.toml`: `safety.allowRunsWithPlayers` (false). Every file the mod writes lives in that folder; nothing goes in the world folder.
- Messages are sent as plain English text read from the mod's own language file on the server, so players' games need nothing installed.
- The project: Forge 1.20.1 mod `bsp_server_stress_test`, server only, BSP-Core 1.4.0 as an optional dependency, the GameTest setup with an empty test structure, and the language file generator and check.
